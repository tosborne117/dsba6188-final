DSBA 6188 · Building with an AI agent

Prompting the RAG Agent App

You can build the RAG Agent Streamlit app with two prompts. Prompt 1 decides what to build and writes PLAN.html. Prompt 2 builds the app exactly as the plan says. You review the plan between the two prompts.

1 · PlanAgent asks questions, compares options, writes PLAN.html. No app code.
→
You reviewRead the plan. Fix it now. A change here is cheap.
→
2 · BuildNew session. Agent follows PLAN.html strictly and tests each part.

Why two prompts?

Choosing an architecture and writing code are two different jobs. When one prompt does both, the agent makes design choices silently while it codes. You find them later, in the code.

Why a new session for Prompt 2?

A new session knows only what PLAN.html says. If something is missing from the plan, you see it as a question from the agent, not as a hidden guess.

Prompt 1 · Plan
I want to build a Streamlit app for my DSBA 6188 project. Do not write any app code in this step. Your job is to help me decide the architecture and the features, and then write the decisions to PLAN.html.

GOAL
[One sentence. Example: A chatbot that answers questions about my PDF equipment manuals and cites the source file and page.]

WHAT I ALREADY KNOW
- Two pages:
  1. Chat: an agent that can call a RAG tool to search my documents.
  2. Create vectors: upload PDFs, split them into chunks, embed the chunks, and store them.
- Vector database: [Qdrant Cloud / Snowflake / both, selected in the sidebar]
- Chat model and embeddings: [Ollama on my computer / Google AI Studio (Gemini) / both]
- All keys and passwords go in a .env file. [Snowflake uses RSA key-pair authentication.]
- Python environment: [path to my venv]

BEFORE YOU WRITE THE PLAN
1. Read the files in this folder. Check which packages are installed in my venv.
2. Ask me up to 5 questions about anything that changes the architecture. Wait for my answers.
3. For each important decision, give 2 options, recommend one, and say why. Important decisions include: the agent framework, the vector store library, the embedding model and its dimension, the chunk size and overlap, and how the user selects a collection or table.

WHAT PLAN.html MUST CONTAIN
- Architecture diagram: pages, Python modules, models, and databases.
- Flow 1 (create vectors) and Flow 2 (chat) as sequence diagrams.
- Draw every diagram as inline SVG.
- Folder structure: every file and its one job.
- Settings table: every .env variable, which part uses it, and its default value.
- Feature list. For each feature, write one acceptance check: one sentence that says how to test that the feature works.
- Design decisions, each with its reason.
- Out of scope: what this version will NOT do.
- Possible next features.

RULES
- Keep the app small enough that I can read and explain every file myself: [about 1,000 lines of Python].
- Write short sentences in active voice. Use one term for each concept.
- PLAN.html is one HTML file that works in light and dark mode.

Review the plan before Prompt 2

Prompt 2 builds exactly what the plan says, including its mistakes. Check these points first:

  • Every feature has an acceptance check that you can actually run.
  • The settings table lists every .env variable. No key is written in the plan itself.
  • The folder structure and the architecture diagram name the same files.
  • The Out of scope list is there. Without it, the agent may add extra features.
  • You understand every design decision. If not, ask the agent: Explain decision X in two sentences.
  • Defaults have real values, for example chunk size 600 and overlap 100. "Reasonable defaults" is not a value.

To change the plan, ask in the same session, for example: Change the plan: use one Qdrant collection per embedding model. Update PLAN.html.

Prompt 2

Build the app from the plan, strictly

Start a new agent session in the same folder. Then paste this prompt.

Prompt 2 · Build
Build the Streamlit app that PLAN.html describes. PLAN.html is the specification. Follow it exactly.

BEFORE YOU CODE
1. Read all of PLAN.html.
2. List the files you will create, in build order, and the acceptance check for each feature.
3. Wait for my OK.

WHILE YOU CODE
- Create only the files, pages, functions, and settings that PLAN.html names. Do not add features, pages, settings, or packages that the plan does not name.
- Use the names and values in the plan exactly: file names, page titles, .env variable names, and defaults such as chunk size and overlap.
- If the plan is unclear, contradicts itself, or cannot work (for example, a package or a model does not exist), stop and ask me. Do not guess. Do not change the plan yourself.
- Never write a key or password in the code. Read every secret from .env. Create .env.example with empty values.
- Use my venv at [path to my venv]. Ask me before you install a package.

TESTING
- After each module, run a check: a unit test, or a headless run with streamlit.testing.v1.AppTest.
- If a database or a model is not reachable, test with a mock connection, and say so.
- Do not say that a feature works unless a test or a live run showed it.

WHEN YOU FINISH, REPORT
- A table: each feature in PLAN.html, its file(s), and its test result (tested / mock only / not tested).
- Every place where the code is different from the plan, and why.
- What I must run myself, for example a live run with my own keys.
- Write README.md with the setup and run steps. Do not edit PLAN.html.

After the build: one change per prompt

Small, specific prompts work best for changes. Give one change per prompt. Test it. Then ask the agent to keep the documents in sync. These are real follow-up prompts from building this app:

  • Show the Qdrant collections in the sidebar. Let me select which collection to query.
  • When I select Snowflake, also show the tables that I can use.
  • If there is no collection or table, ask the user to type a name first.
  • Change the default chunk size to 600 and the overlap to 100.
  • Update README.md and PLAN.html.

The last prompt matters. If you skip it, PLAN.html and README.md stop matching the app, and the next agent session starts from a wrong specification.

Extra prompt · Snowflake only

Create a Snowflake key pair

Snowflake uses an RSA key pair to sign you in. Use this prompt once, before your first live Snowflake test. It works on Windows and macOS, and needs no OpenSSL.

Extra prompt · Key pair
Write a Python script, keys/make_keys.py, that creates an RSA key pair for Snowflake key-pair authentication. I use [Windows / macOS]. The script must work on both.

REQUIREMENTS
- Use the "cryptography" package. Do not use OpenSSL or other tools.
- Key size: 2048 bits.
- Write two files in the keys/ folder:
  1. rsa_key.p8: the private key, PKCS#8, PEM format, not encrypted.
  2. rsa_key.pub: the public key, PEM format (SubjectPublicKeyInfo).
- If either file already exists, stop with a clear message. Never overwrite a key.
- Make rsa_key.p8 readable only by me: icacls on Windows, chmod 600 on macOS.
- At the end, print the SQL I must run in Snowflake:
  ALTER USER <my_user> SET RSA_PUBLIC_KEY='<public key text on one line, without the BEGIN/END lines>';
- Never print the private key.
- Make sure .gitignore excludes keys/*.p8.

BEFORE YOU FINISH
- Run the script in a temporary folder. Check that the public key made from rsa_key.p8 matches rsa_key.pub.
- Explain each step of the script in two or three short sentences.
  • Private key (rsa_key.p8): stays on your computer. Never share it or upload it.
  • Public key (rsa_key.pub): goes to Snowflake through the ALTER USER statement.
  • Then set SNOWFLAKE_PRIVATE_KEY_PATH=keys/rsa_key.p8 in .env.
